CFCT CHURCH MANAGEMENT SYSTEM
DOKUMENTI KAMILI YA MFUMO (KWA UHAMISHO KWENDA WORD)
Tarehe: 06 Mei 2026

=====================================================================
1. MUHTASARI WA MFUMO
=====================================================================

CFCT Church Management System ni mfumo wa kidigitali wa kusimamia shughuli za kanisa kwa ngazi nyingi za uongozi (Taifa, Zone, Mkoa, Wilaya, Local Church). Mfumo una sehemu kuu mbili:

1) Frontend: React + Vite + Tailwind CSS
2) Backend: Django + Django REST Framework + PostgreSQL (production) + SQLite (tests)

Mfumo unahudumia:
- Usimamizi wa watumiaji na majukumu (roles)
- Usimamizi wa hierarchy ya makanisa
- Usajili wa wanachama na approvals
- Matukio (events)
- Matoleo na taarifa za kifedha
- Mahudhurio kwa QR check-in
- Idara na maombi ya kujiunga idarani
- Uhamisho wa waumini
- Maombi ya maombi (prayer requests)
- News/CMS
- Notifications
- Audit logs

=====================================================================
2. JINSI MFUMO UNAVYOFANYA KAZI (WORKFLOW YA JUMLA)
=====================================================================

2.1 Login na Session
- Mtumiaji anaingia kwa username/password.
- Mfumo hutumia JWT:
  - Access token: saa 1
  - Refresh token: siku 7
- Token rotation + blacklist zipo, hivyo logout inafuta uwezo wa kutumia refresh token ya zamani.

2.2 Registration na Verification
- Mtumiaji mpya anaweza kusajiliwa.
- Mfumo unatuma verification link ya email.
- Baada ya verification, akaunti huenda kwenye mchakato wa approval kulingana na role/hierarchy.

2.3 Authorization (Nani anaona nini)
- Kila role huona data ya scope yake kupitia get_accessible_churches logic.
- National leader huona scope ya juu zaidi.
- Local roles huona data ya local church au descendants wake kulingana na role.

2.4 Data Operations
- CRUD nyingi zinafanyika kupitia API viewsets.
- Frontend pages hutumia service layer kufanya calls kwenda backend.
- Admin panel ya Django ipo kama control center ya usimamizi wa data na matengenezo.

=====================================================================
3. MUUNDO WA ROLE NA WAJIBU (RBAC)
=====================================================================

Roles zilizopo:
1) national_leader
2) zone_leader
3) regional_leader
4) district_leader
5) local_leader
6) local_member
7) finance_team

3.1 Kile role inaweza kufanya (kwa ujumla)

A) national_leader
- Anaweza kuona/simamia mfumo mzima
- Anaweza kusimamia users kwa kiwango cha juu
- Anaweza kuona audit logs
- Anaweza kusimamia CMS na reports za juu

B) zone_leader
- Anaweza kusimamia data ya zone yake na ngazi zilizo chini
- Anaweza kufanya approvals/management ndani ya scope yake

C) regional_leader
- Anaweza kusimamia data ya region yake na ngazi za chini

D) district_leader
- Anaweza kusimamia district na local churches zilizo chini yake

E) local_leader
- Anaongoza local church yake
- Anaweza kusimamia events, departments, baadhi ya approvals za local

F) local_member
- Anaona huduma za mwanachama (mfano attendance history, giving history, baadhi ya pages za taarifa)
- Hana mamlaka ya management ya juu

G) finance_team
- Ana mamlaka maalum kwa financial reports/oversight kulingana na policy ya mfumo

3.2 Kile role hawezi kufanya (kwa ujumla)
- local_member hawezi kufanya administrative approvals za mfumo mzima
- local_leader hawezi kufanya national-level governance
- zone/regional/district leaders hawana mamlaka yanayozidi scope yao
- finance_team si mbadala wa uongozi wa hierarchy ya users/church tree

=====================================================================
4. ULINZI WA MFUMO (SECURITY)
=====================================================================

4.1 Authentication Security
- JWT imewekwa kwa muda wa matumizi unaodhibitiwa.
- Logout endpoint ipo na token blacklist imewezeshwa.

4.2 Brute-force Protection
- Login lockout policy ipo:
  - max failed attempts
  - lockout window
  - lockout duration

4.3 Throttling
- API rate limits kwa anonymous na authenticated users zipo.
- Login endpoint ina throttle maalum.

4.4 CORS/CSRF
- CORS imewekewa allowed origins kwa local development (3000/5173) + env control.
- CSRF settings na secure headers zipo.

4.5 Password Reset
- Password reset flow ipo (request + confirm) kwa token salama.

4.6 Email Verification
- email_verified flag + token + timeout zipo.

4.7 Auditability
- Audit logs zipo (hasa kwa privileged view).

5. ADMIN PANEL YA DJANGO (NINI KINAWEZEKANA)
=====================================================================

Admin panel ni sehemu muhimu ya usimamizi wa operational data.

5.1 Accounts Admin
- Kuunda, kuhariri, kuapprove, kuactivate/deactivate users
- Role assignment
- Search/filter kwa role, status, church

5.2 Churches Admin
- Kusimamia hierarchy ya church structure
- Parent-child assignment kwa ngazi zote
- Usimamizi wa zone/region/district/local mappings

5.3 Members Admin
- Kusimamia member registrations
- Approve/reject workflows
- Bulk actions
- Validation ya taarifa za usajili

5.4 Offerings Admin
- Kusimamia records za matoleo
- Verification fields
- Filter/reporting ya msingi kwa entries

5.5 Finance Admin
- Kusimamia financial transactions
- Date hierarchy + categorization

5.6 Attendance Admin
- Attendance records summary
- Attendance check-in records
- Filters za service/church/date

5.7 Events/News/Departments/Transfers/Prayers/Notifications/CMS
- CRUD za modules husika
- Operational management ya maudhui na workflows

5.8 Mambo ya kuzingatia kwa Admin Panel
- Ruhusa za admin users zinapaswa kudhibitiwa kwa umakini.
- Superuser access iwe ya watu wachache.
- Audit trail ya admin actions ifuatiliwe.

6. HALI YA UKAMILIFU WA MFUMO (COMPLETION STATUS)
=====================================================================

Kiwango cha jumla (makadirio ya sasa):
- Core functionality: Kimekamilika vizuri
- Security baseline: Kipo vizuri
- Operational readiness: Kiko juu, ila kuna maboresho muhimu

6.1 Sehemu zilizokamilika kwa kiwango kizuri
- JWT auth + token blacklist
- Role hierarchy na scoped access
- Member management + approvals
- Events msingi + listing
- Offerings + sehemu ya financial reporting
- Attendance QR check-in flow
- Transfers workflow
- Departments + join request flow
- Notifications msingi
- Admin panel coverage kwa modules nyingi

6.2 Sehemu zenye ukamilifu wa kati (partial)
- Baadhi ya ripoti za kifedha zinaweza kuhitaji uboreshaji wa aggregation/consistency
- Celery iko configured, lakini matumizi ya asynchronous tasks yanaweza kuongezwa zaidi
- CMS ipo lakini inahitaji data governance na UX polish ya kudumu

6.3 Sehemu zinazohitaji kuongezwa au kurekebishwa (priority)

PRIORITY YA JUU:
1) Audit log retention policy
- Weka cleanup schedule ili logs zisikue bila mipaka.

2) 2FA kwa viongozi wa juu
- Ongeza two-factor auth kwa roles nyeti (national/zone/regional).

3) Payment callback hardening
- Hakikisha webhook signature verification imekamilika kikamilifu.

PRIORITY YA KATI:
4) API documentation rasmi (OpenAPI/Swagger)
- Irahisishe integrations na onboarding.

5) Bulk member import
- Kwa sasa export ipo; ongeza import yenye validation.

6) Request correlation ID
- Kuboresha tracing/debugging across services.

PRIORITY YA CHINI:
7) Session policy explicit tuning
8) Data governance workflows (retention + archive standards)
9) UI/UX polish endelevu kwenye baadhi ya pages zenye data ndefu

=====================================================================
7. UCHAMBUZI WA RISK NA MAPENDEKEZO YA UENDESHAJI
=====================================================================

7.1 Risks kuu
- Credential compromise kwa viongozi wa juu bila 2FA
- Kukua kwa audit logs bila retention
- Inconsistency kwenye baadhi ya asynchronous/background tasks ikiwa worker haijaendeshwa vizuri

7.2 Mapendekezo ya haraka (30-60 siku)
- Tekeleza 2FA kwa leaders
- Tekeleza audit cleanup schedule
- Hakikisha Celery worker + beat + Redis vinafanya kazi production
- Andika na tumia runbooks za incident response

7.3 Mapendekezo ya kati (60-120 siku)
- OpenAPI docs + endpoint governance
- Standardized error response format across APIs
- Advanced report validation tests

=====================================================================
8. MAELEKEZO YA UENDESHAJI WA KILA SIKU (OPS)
=====================================================================

8.1 Kabla ya kuanza production
- Hakikisha DEBUG=False
- Hakikisha ALLOWED_HOSTS, CORS_ALLOWED_ORIGINS, CSRF_TRUSTED_ORIGINS zimewekwa sahihi
- Hakikisha SECRET_KEY imehifadhiwa salama
- Hakikisha DB backups zipo na zimepangwa
- Hakikisha EMAIL settings za production zipo

8.2 Services za lazima
- Django backend (gunicorn/uvicorn au run strategy ya prod)
- PostgreSQL
- Redis (ikiwa Celery inatumika)
- Celery worker + Celery beat
- Reverse proxy (Nginx) kwa TLS/headers

8.3 Monitoring ya msingi
- API error rates
- Login failures/lockouts
- Payment callback failures
- Queue lag ya Celery
- DB disk growth (hasa audit logs)
